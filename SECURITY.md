# Security

## Reporting a vulnerability

This is a personal/learning project without a dedicated security contact. If you find a vulnerability, please open a GitHub issue (or, for something you'd rather not disclose publicly, reach out to the maintainer directly via GitHub) rather than a public pull request.

## The privileged Jobs: this operator's highest-risk operations

Everything else in this operator is bounded by ordinary Kubernetes RBAC: list/watch/patch calls against the API server, scoped by a `ClusterRole`. Two operations are fundamentally different in kind, not just degree, and both use the same `nsenter`-based pattern: the `kubeadm`/`generic` provider adapters' `InPlace` strategy runs a privileged, node-pinned **upgrade Job** that mutates a real host's OS state directly (install a new `kubeadm`/`kubelet`, restart `kubelet`); and the control-plane precheck gate runs a privileged, node-pinned **etcd health-check Job** that reads (never mutates) a real host's etcd client certs and queries its local etcd member directly. Both are intentional container-escape-as-a-feature — there's no way to do either from inside a Kubernetes cluster without re-entering the host's own namespaces. They deserve more scrutiny than everything else in this codebase, and this document exists so that scrutiny is written down rather than scattered across design discussions.

### What this looks like: a node-pinned, short-lived, privileged Job

- **Node-pinned**: `spec.nodeName` is set directly on the pod, bypassing the scheduler. This is deliberate, not incidental — for the upgrade Job specifically, it's also what lets it still land on a node that's already been cordoned by the `Draining` phase (cordoning only blocks the *scheduler*).
- **Short-lived**: each Job exists only for the duration of one action. `TTLSecondsAfterFinished` cleans it up after completion (600s for the upgrade Job; 30s for the etcd health check, since that one is created fresh, deleted, and recreated on every retry while unhealthy rather than once per node per hop, so a stale result should not linger anywhere near as long); `ActiveDeadlineSeconds` bounds how long either is allowed to run *before* completion, so a hung attempt can't linger indefinitely.
- **Privileged, but narrowed per Job to exactly what each one needs**, rather than blanket `privileged: true`:
  - The **upgrade Job** re-enters `--mount --uts --ipc --net --pid` and needs `SYS_ADMIN` (the `setns()` calls `nsenter` makes), `SYS_CHROOT`, and `SYS_PTRACE` (opening `/proc/1/ns/*` at all requires it, independently of `SYS_ADMIN`, which only covers the subsequent `setns()` call).
  - The **etcd health-check Job** needs no `--uts`/`--ipc` (it touches neither), narrowing its namespace set to `--mount --net --pid` — but still needs the *same* three capabilities: `SYS_CHROOT` turned out to be load-bearing for `nsenter --mount` too, confirmed empirically against a real cluster (`nsenter: reassociate to namespace 'ns/mnt' failed: Operation not permitted` with only `SYS_ADMIN`+`SYS_PTRACE`) — its mount-namespace reassociation invokes a chroot-adjacent syscall to keep the calling process's working directory sane. Narrowing the namespace set turned out to be the available lever here, not the capability set.
  - `AllowPrivilegeEscalation: false` and `ReadOnlyRootFilesystem: true` are set on both.

### Blast-radius containment

- **A dedicated namespace** (`config/executor/`), separate from the manager's own, shared by both Jobs (no reason to duplicate this infrastructure per Job — the isolation boundary that matters is manager-vs-executor, not upgrade-vs-healthcheck). Only this namespace runs at the Kubernetes **`privileged` Pod Security Standard**; everything else this operator touches, including the manager's own namespace, runs at `restricted`. This is deliberate isolation, not an oversight — an earlier draft of this design ran the executor in the *manager's* namespace, which would have meant either weakening the whole deployment's PSA level or having the executor Jobs get rejected by admission control outright. Keeping the manager's own footprint minimal and auditable, while being explicit about exactly where the real risk concentrates, is the point.
- **A dedicated ServiceAccount** with **zero RBAC grants**, shared by both Jobs — no `RoleBinding` exists for it anywhere, because neither container talks to the Kubernetes API at all; each only runs local host commands. `automountServiceAccountToken: false` is set on both the `ServiceAccount` and each pod template as two independent enforcement points, so there's no token to abuse even if an image were compromised.
- **No host filesystem mount.** An earlier draft mounted the host's entire root filesystem into the container via `hostPath` — but the script never referenced it. `nsenter --mount` switches the *process itself* into the host's real mount namespace; paths resolve against the real host filesystem directly once that happens, with no bind-mount needed at all. Removing it was a strict security improvement with zero functionality lost: a full read-write view of the host filesystem, sitting unused, is exactly the kind of thing that should not exist.
- **Minimal image content, shared by both Jobs.** The container image (`images/kubeadm-executor/`) only needs `nsenter` (from `util-linux`), `tar` (already present in the base image, needed to extract `etcdctl` from its release archive), and a shell — nothing else. Every other command either script runs (`curl`, `dpkg`/`dnf`, `kubeadm`, `etcdctl`, `systemctl`) executes *after* `nsenter` switches namespaces, meaning it resolves against the **host's** own binaries, not anything bundled in the image. Less software inside a container that runs with `SYS_ADMIN` is less attack surface, full stop. (The upgrade script originally shelled out to `apt-get` for the kubelet package swap; that was replaced with a direct `.deb` fetch + `dpkg -i`, since `apt-get` needs write access to `_apt`-owned directories this capability set does not grant — see the note in `images/kubeadm-executor/upgrade.sh`.)
- **Both scripts are baked into the image**, not injected at Job-creation time by the operator's Go code. This matters for digest pinning to mean anything: if the actual behavior could be changed independently of the image (e.g. by editing a string constant in the controller and redeploying), pinning the image's digest wouldn't actually capture "what runs" — it'd just be pinning an inert shell interpreter.

### Supply-chain integrity of the fetched binaries

Both scripts verify a SHA-256 checksum before installing or trusting anything they fetch, from CDN-configurable base URLs (`KUBEADM_RELEASE_BASE_URL`, `KUBE_DEB_REPO_BASE_URL`, `OS_PACKAGE_ARCHIVE_BASE_URL`, `ETCD_RELEASE_BASE_URL` — air-gapped deployments can point any of them at an internal mirror): the upgrade script fetches `kubeadm` from the official Kubernetes release CDN, the matching `kubelet` `.deb` from the Kubernetes package repo, and (if missing) `kubelet`'s own plain dependencies from the host distro's own archive; the etcd health-check script fetches `etcdctl`, version-matched to whatever etcd the cluster is actually running (read from the live `etcd` pod's own image tag, not assumed), from the official etcd release CDN. This is the load-bearing integrity control for every one of these steps — **not network-level restriction**. A Kubernetes `NetworkPolicy` on the executor namespace cannot constrain any of these downloads: they happen after `nsenter --net` switches the process into the host's own network namespace, which structurally exits the pod network layer `NetworkPolicy` enforces at. Any egress restriction on that traffic would need to happen at the host/infrastructure level (node firewall rules, DNS/egress controls) — outside what this operator can enforce from inside the cluster. If this were ever extended to run a network-touching step *before* `nsenter`, that step would be the one place a `NetworkPolicy` could actually bind.

#### Where the expected checksums come from

The expected SHA-256 for `kubeadm`, the `kubelet` `.deb`, and the `etcdctl` tarball is **pinned** in a known-good table compiled into the manager binary (`pkg/checksums/checksums.yaml`, `go:embed`'d — regenerate with `hack/update-checksums.sh`). The manager looks up the entry for the exact `(target version, node architecture)` being upgraded and passes it to the Job as `KUBEADM_SHA256` / `KUBELET_DEB_SHA256` / `ETCDCTL_SHA256`. The scripts verify against that value and nothing else.

This is deliberately **not** the same as "download the artifact and the `.sha256`/`SHA256SUMS` file served next to it and check they match." That only proves the bytes weren't corrupted in transit — an attacker who controls the mirror (or the CDN, or the path in between) serves a malicious binary *and* a matching checksum, and the check passes. Pinning a digest that was recorded out-of-band, ahead of time, is what actually detects a swapped artifact.

Consequences of pinning:

- **Fail-closed for unknown versions.** If a `(version, arch)` pair isn't in the table, the Job refuses to run rather than fetching something it can't verify against a trusted value. Adding a new target Kubernetes/etcd version means regenerating the table first.
- **Escape hatch, off by default.** Setting `ALLOW_UNPINNED_CHECKSUMS=true` on the manager (`--set` env in the Deployment) downgrades the behavior to the fetch-alongside integrity check described above, with a loud warning in the Job logs. It exists for development and for genuinely urgent patch upgrades ahead of a table update; it is not a normal operating mode.
- **The host distro dependencies (`socat`, `ebtables`, `conntrack`, …) are still not pinned** — they're fetched from the distro archive's own `Packages.gz` index and verified against the `SHA256` field in that same index. This is a narrower gap: the set of possible packages is the distro's, not attacker-chosen, and the index is itself normally signed by the distro (the scripts don't verify that signature). Pinning these too would mean tracking a much larger, per-distro-release matrix; it's a documented known limitation, not an oversight.

### Known follow-up: image pinning by digest

`ExecutorImage`'s default is currently a mutable tag (`:latest`), not a content-addressed digest (`@sha256:...`). Pinning by digest is the correct production practice — it means whoever controls the image tag can't silently swap in different content — but there's no real digest to pin to until the image is actually built and published somewhere. This is a deployment-configuration follow-up once that happens, not a code change.

### Alternatives considered, and why this one was kept

| Approach | Lowers the ceiling of what a compromise achieves? | Real tradeoff |
|---|---|---|
| **Privileged Job + `nsenter`** (this design) | No — `nsenter --mount` with `SYS_ADMIN` is full host control by definition; no capability-narrowing trick changes that ceiling | Short-lived and node-pinned, so the *window* of exposure is minimized even though the *ceiling* isn't |
| Persistent DaemonSet-based agent | No — needs the same capability for the same job | Worse on one axis: an always-running privileged process on every node has a larger, longer-lived attack surface than a Job that exists only for one action |
| SSH-based external orchestration | No — whoever holds the SSH key has root everywhere; same ceiling, different vector | Trades "compromised image / Job-creation RBAC" for "leaked SSH secret," plus real key-rotation burden, plus requires pre-provisioned SSH access this operator is explicitly designed not to assume |
| Never mutate in place — always re-image via out-of-band bare-metal provisioning (PXE/Tinkerbell/MAAS-style) | Yes — genuinely eliminates in-cluster privileged mutation | Not a hardening tweak on this design, a different and much larger system; it would also remove the reason `InPlace` exists at all, since the audience most likely to need it (on-prem kubeadm clusters) is also the audience least likely to already have that provisioning infrastructure |

The honest conclusion: this operation is, and will remain, the single highest-risk thing in this codebase, by design — the job itself (mutate a real host's OS with no pre-provisioned access) inherently requires it. The response to that isn't a different architecture, it's treating it with more rigor than everything else here, which is what this document is meant to hold accountable over time.
